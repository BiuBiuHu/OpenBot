## 1. 当前决策

- 当前产品决策：一条聊天里有四种能力。本机主服务负责分发和少数已证实必须本地完成的短路径（时钟、含糊改代码、查找、公开文档 URL）。ECS 上的 OpenHands 负责有电脑的事。公开网页不是第三台电脑，也不是用户文档库。
- 被拒绝的替代方案：把四种能力做成四个 mode；把「讲了什么」交给 OpenHands 当电脑任务；用搜索摘要冒充读过链接；在本增量做上传/工作区文稿产品。
- 当前范围边界：本增量 = 功能文档落盘 + 公开文档 URL 阅读（含评测）。不部署。桌面壳保持 main 已有行为。

## 2. 需求验证结论

- 需求验证文档：`docs/openbot-agent-capabilities/01-product/requirement-validation.md`
- 已消除的歧义：公开 URL 阅读 ≠ 文档库；「只分发」不覆盖本增量文档问句；决策源是本目录。
- 仍需确认的问题：无（用户已要求推进）。
- 不进入本版本的内容：REQ-CODE-001、REQ-WSDOC-001、REQ-DESK-001 的新实现。

## 3. 目标澄清

- 用户真正想完成的业务结果：在自己的笔记本页上，用一句话让 OpenBot 办事：闲聊、改自己电脑上的代码、读/写自己在乎的文稿、看着并接管那台电脑的桌面。立刻要修的是：贴公开文档链接问内容时，必须真的读到并短答。
- 主要用户/角色：本机使用者。
- 核心工作流：同一输入框 → 主服务分流 → 文档则 HTTP 读页 → 几句人话。其它能力按 backlog 分期。
- 工作单元和批量范围：一条消息。
- 成本、时效和质量约束：文档抓取约 8s；几句话；默认简体；无新计费生成。
- 返工/重试/回滚方式：再说一次；git 回滚。
- 用户已确认结论：见需求验证 §2。

## 4. 用户、问题与场景

### 4.1 用户与角色

一个人，笔记本浏览器打开 `http://127.0.0.1:<port>/`。没有运营后台。

### 4.2 要解决的问题

人把公开文档链接贴进聊天问「讲了什么」，系统却去开 ECS 电脑任务，超时后只回「这台电脑这轮没在时限里跑完。你再说一次就行。」——看起来像不会读文档。

### 4.3 触发场景和使用频率

- 高频本增量：`看看 https://github.com/…/blob/…/chapter3.md 这个文档讲了什么?`
- 已有、保持：你是谁、现在几点、Grok Bot 是什么、含糊「改代码」、超时润色。
- 后续：把 `src/foo.ts` 改成…、在工作区写 `notes.md`、看着桌面点一下。

### 4.4 当前替代方案和痛点

人自己打开链接读。或等 OpenHands 浏览器，但时限内完不成。旧阶段笔记互相打架，评审没有单一决策源。

## 5. 范围

### 5.1 In Scope

- 本目录一份主文档一类，简体中文，模板齐全。
- `isDocumentReadAsk` + `readPublicDocument` + `voiceFromDocument`。
- GitHub blob → raw。
- eval `read-public-doc` 与单元测试。
- `docs/phases/` 顶部标明已被本目录替代。

### 5.2 Out of Scope

- 生产/预发部署。
- 文档库、上传、权限、网盘。
- 具名改代码产品验收。
- 新的桌面交互（最大化/无工具条已在 main）。
- 打印或入库任何密钥、公网 IP、PEM。

### 5.3 权限和环境范围

单人本机。出网仅公开 HTTP。VNC 仍只环回。

## 6. 核心流程

### 6.1 主流程

1. 人在唯一输入框发送。
2. 主服务 `runThreadTurn`：
   - 时钟 → 上海时间。
   - 含糊改代码 → 「可以。说一下改哪个文件…」
   - **文档问句 → HTTP 读页 →「我看过了。」+ 标题/两句。**
   - 查找 → 搜索（必要时才 page-browse）。
   - 其余 → 交接 OpenHands。
3. 回复进同一线程。语言 = Settings。

### 6.2 状态流转

无文档对象。消息级：thinking → token → done。

### 6.3 异常、空态和失败路径

读不成：一句「这个链接我没读成。」真电脑任务超时：仍用原超时句，但**不得**用在文档路径。

### 6.4 成本保护和返工流程

不调模型。人改口重发。无强制覆盖、无批量。
